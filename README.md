# 토큰 베팅 학급 자리 배치

토큰 100개를 원하는 자리에 걸고, 교사가 한 번 추첨해서 자리를 정하는 실시간 웹 앱입니다.
GitHub Pages(정적 호스팅)와 Firebase Realtime Database 무료 요금제(Spark)만으로 동작합니다. 서버 코드는 없습니다.

구성 파일은 다음과 같습니다.

- index.html: 앱 전체(HTML, CSS, JS 단일 파일)
- database.rules.json: 권한 설계를 강제하는 보안 규칙
- sample_roster.csv: 예시 명단(학번, 이름) 31명
- firebase.json, package.json, tests/: 규칙을 배포하고 테스트하기 위한 보조 파일(앱 실행에는 필요 없음)

## 0. 먼저 데모로 체험하기

Firebase 설정 없이 바로 써 볼 수 있습니다. index.html을 정적 서버로 열고 주소 끝에 `?demo=1`을 붙입니다.

```
python3 -m http.server 8765      # 저장소 폴더에서 실행
http://localhost:8765/index.html?demo=1
```

데모 모드는 브라우저 메모리 안의 가짜 백엔드로 동작합니다. 보안 규칙의 읽기·쓰기 제한도 흉내 내므로 클라이언트가 규칙에 어긋나는 접근을 하면 데모에서도 실패합니다.

- 학생 입장: 방 코드 demo, PIN 123456, 학번 30101, 이름 김민준(명단 순서는 sample_roster.csv와 같습니다)
- 교사 체험: 로그인 화면의 "교사로 체험하기"
- 우측 상단 "데모 도구": 가상 학생 31명이 분산 베팅하는 시뮬레이션, 추첨 자체 검증(1,000회), 데모 초기화

데모 도구의 자체 검증은 다음 세 가지를 콘솔과 화면에 출력합니다.

1. 경쟁자 없는 단독 베팅은 항상 당첨되는가
2. 같은 자리에만 건 두 학생의 당첨 비율이 토큰 비율과 일치하는가(30:10, 50:50, 5:95, 통계 검정 |z|<3.5)
3. 근접 금지 쌍을 입력했을 때 무작위 배치 단계의 위반이 0건인가

## 1. Firebase 프로젝트 만들기

1. [Firebase 콘솔](https://console.firebase.google.com/)에서 "프로젝트 추가"를 누르고 이름을 정합니다. Google 애널리틱스는 필요 없으니 꺼도 됩니다.
2. 요금제는 Spark(무료)를 그대로 둡니다.

## 2. Realtime Database 만들기

1. 왼쪽 메뉴 "빌드 → Realtime Database → 데이터베이스 만들기"를 누릅니다.
2. 위치(리전)를 고릅니다. 한국에서 쓴다면 asia-southeast1(싱가포르)이 가장 가깝습니다. 학생 이름과 학번이 이 리전의 서버에 저장되므로, 학교의 개인정보 지침을 확인한 뒤 고르세요. 리전은 만든 뒤에 바꿀 수 없습니다.
3. 보안 규칙은 "잠금 모드로 시작"을 고릅니다. 곧 아래 6단계에서 규칙을 교체합니다.
4. 만들어진 뒤 데이터 탭 상단에 보이는 주소(`https://프로젝트-default-rtdb.asia-southeast1.firebasedatabase.app` 형태)를 복사해 둡니다. 4단계에서 씁니다.

## 3. Authentication 켜기

"빌드 → Authentication → 시작하기 → Sign-in method"에서 두 가지를 사용 설정합니다.

- 익명: 학생용
- 이메일/비밀번호: 교사용

## 4. 웹 앱 등록과 firebaseConfig 붙여넣기

1. 프로젝트 개요 옆 톱니바퀴 → "프로젝트 설정 → 내 앱 → 웹(</>)"으로 앱을 등록합니다. Firebase Hosting 설정은 체크하지 않습니다.
2. 화면에 나오는 firebaseConfig 값을 index.html 상단의 `firebaseConfig`에 붙여넣습니다.

```js
const firebaseConfig = {
  apiKey: "...",
  authDomain: "프로젝트.firebaseapp.com",
  databaseURL: "https://프로젝트-default-rtdb.asia-southeast1.firebasedatabase.app",
  projectId: "...",
  appId: "..."
};
```

주의할 점이 있습니다. 앱을 등록한 시점에 Realtime Database가 아직 없었다면 `databaseURL`이 빠져 있을 수 있습니다. 이때는 2단계에서 복사한 주소를 직접 적어 넣으세요. 이 값이 비어 있으면 데이터베이스에 연결되지 않습니다.

이 설정값은 공개되어도 괜찮은 식별자입니다. 데이터는 6단계의 보안 규칙이 지킵니다. 다만 Google Cloud 콘솔의 "API 및 서비스 → 사용자 인증 정보"에서 이 API 키의 HTTP 리퍼러를 `https://사용자명.github.io/*`로 제한해 두면 남용을 더 줄일 수 있습니다(선택).

## 5. 교사 계정 만들기와 /admins 등록

교사 권한은 로그인만으로는 생기지 않습니다. Realtime Database의 `/admins/{uid}`가 true인 계정만 관리 권한을 가집니다.

1. "Authentication → Users → 사용자 추가"에서 교사 이메일과 비밀번호로 계정을 만듭니다.
2. 만들어진 사용자의 "사용자 UID"를 복사합니다.
3. "Realtime Database → 데이터" 탭에서 루트 옆 `+`를 눌러 이름에 `admins`를 만들고, 그 아래에 이름을 방금 복사한 UID, 값을 `true`로 추가합니다.

```
(루트)
└─ admins
   └─ <교사 UID>: true
```

앱에서 교사 로그인을 했는데 "관리자로 등록되지 않은 계정"이라고 나오면, 그 메시지에 적힌 UID를 그대로 `/admins/` 아래에 추가하면 됩니다.

## 6. 보안 규칙 배포

둘 중 편한 방법을 쓰세요.

방법 A, 콘솔에 붙여넣기: "Realtime Database → 규칙" 탭에 database.rules.json의 내용을 그대로 붙여넣고 "게시"를 누릅니다.

방법 B, Firebase CLI:

```
npm install -g firebase-tools
firebase login
firebase use --add            # 프로젝트 선택
firebase deploy --only database
```

규칙을 배포하지 않으면(잠금 모드 그대로면) 모든 접근이 거부되어 앱이 동작하지 않습니다. 반대로 테스트 모드(누구나 읽기·쓰기)로 두면 보안이 사라지므로 절대 그렇게 두지 마세요.

## 7. 승인된 도메인 추가와 GitHub Pages 배포

1. "Authentication → Settings(설정) → 승인된 도메인 → 도메인 추가"에 `사용자명.github.io`를 추가합니다. 경로(`/저장소이름`)는 쓰지 않고 도메인만 적습니다. 익명·이메일 로그인만 쓰는 지금 구조에서는 이 목록이 동작에 영향을 주지 않을 수도 있지만, 추후 로그인 방식을 늘려도 문제가 없도록 등록해 두는 것을 권장합니다.
2. 이 저장소를 GitHub에 올립니다(index.html이 저장소 최상위에 있어야 합니다).
3. 저장소 "Settings → Pages"에서 Source를 "Deploy from a branch"로 하고, 브랜치(main 등)와 `/ (root)`를 선택해 저장합니다.
4. 1~2분 뒤 `https://사용자명.github.io/저장소이름/`로 접속됩니다.

## 8. 수업에서 쓰는 순서

사전 준비(교사)

1. 교사 계정으로 로그인합니다.
2. ⚙️ → 방: 방 코드와 6자리 PIN을 정해 방을 만듭니다. 테스트용 방과 실사용 방을 따로 만들 수 있습니다. PIN은 해시로만 저장되어 다시 볼 수 없으니 기억해 두거나, 잊으면 "PIN 재설정"으로 다시 정하세요.
3. ⚙️ → 자리 구조: 행·열, 분단 수, 짝꿍/시험대형, 분단 간격, 창문·복도 좌우반전, 교탁 위치를 정하고, 자리를 눌러 쓰지 않는 자리를 ✕로 막습니다. 명단 인원과 활성 자리 수가 다르면 경고가 뜹니다.
4. ⚙️ → 명단: CSV(학번,이름)를 올립니다. UTF-8과 CP949(엑셀 기본 저장)를 자동으로 구분하고, 저장 전에 미리보기에서 중복·빈칸을 알려 줍니다.
5. ⚙️ → 근접 금지(선택): 붙어 앉지 않아야 하는 학번 쌍을 한 줄에 한 쌍씩 적습니다.

수업 시간

1. [베팅 시작]을 누르고, 학생들에게 주소·방 코드·PIN을 알려 줍니다.
2. 학생은 방 코드, PIN, 학번, 이름으로 입장해 자리마다 토큰을 걸고 [베팅 확정하기]를 누릅니다. 마감 전까지 몇 번이든 고쳐서 다시 확정할 수 있습니다.
3. 제출 현황판에서 미제출자와 입장 여부를 확인합니다. 학생이 기기를 바꿔야 하면 해당 학생의 [초기화]를 누릅니다.
4. [베팅 마감] → [🎰 대혼돈 추첨 시작]. 교사 화면이 TV 모드(전체화면)로 바뀌며 연출이 재생됩니다. 연출이 끝나면 자동으로 결과가 학생들에게 공개됩니다.
5. 마음에 들지 않는 자리는 [🔀 자리 수정 모드]에서 두 자리를 차례로 눌러 서로 바꿉니다. 근접 금지 쌍이 붙게 되면 경고 후 강행 여부를 묻습니다. 교환 내역은 기록됩니다.
6. 다음 회차는 [새 회차 시작]으로 베팅·합계·결과를 지우고 모두 토큰 100개로 되돌립니다.
7. 사용을 마치면 ⚙️ → 데이터 → "명단·베팅·결과 일괄 삭제"로 개인정보를 정리합니다.

TV 화면은 교사 화면의 [📺 TV] 버튼으로 엽니다. 브라우저 정책상 소리는 사용자가 한 번 클릭한 뒤에 납니다. 음소거 버튼이 있습니다.

## 9. 추첨 방식

토큰 1개는 추첨권 1장입니다.

1. 남은 모든 유효 (학생, 자리) 베팅 쌍을 토큰 수에 비례한 확률로 하나 뽑습니다.
2. 그 학생을 그 자리에 앉히고, 그 학생의 나머지 베팅과 그 자리에 걸린 다른 베팅을 버립니다.
3. 베팅 쌍이 없어질 때까지 반복합니다. 이 단계에서는 근접 금지를 적용하지 않습니다.
4. 남은 학생(낙첨자, 미제출자)을 남은 활성 자리에 무작위로 앉힙니다. 근접 금지 쌍이 있을 때만 이 단계에서 백트래킹으로 제약을 만족하는 배치를 찾습니다.

근접의 정의는 체비쇼프 거리 1 이내(상하좌우와 대각선)이고, 분단 사이 통로를 가로지르는 자리는 인접으로 보지 않습니다.

유효성 검증은 교사 클라이언트가 원본 bets를 읽어서 합니다. 음수, 정수가 아닌 값, 합계 100 초과, 비활성 자리, 미등록 학번 중 하나라도 있으면 그 학생의 베팅 전체를 무효로 하고 교사 화면에 사유를 표시합니다. 확정하지 않은 학생의 데이터는 제출로 보지 않습니다.

추첨은 교사 기기에서 단 한 번 계산되고, 결과·난수 시드·단계별 추첨 로그가 DB에 저장됩니다. TV와 학생 화면은 저장된 결과를 표시할 뿐 다시 계산하지 않습니다. 같은 입력과 같은 시드로는 항상 같은 결과가 나옵니다.

근접 금지 제약이 베팅 당첨 결과 때문에 불가능하면(두 학생이 베팅으로 붙어 앉게 된 경우 등), 위반을 최소로 하는 배치를 저장하고 위반 쌍을 교사 화면에만 알립니다. 재추첨은 하지 않으며 자리 수정 모드에서 교환해 해결합니다.

## 10. 보안 설계와 한계

원칙은 클라이언트 코드가 전부 공개된다고 가정하는 것입니다. 그래서 민감한 정보는 코드에 넣지 않고 규칙으로 보호합니다.

- 교사: 이메일/비밀번호 로그인 + `/admins/{uid}` 등록. 등록된 uid만 모든 방을 읽고 쓸 수 있습니다.
- 방 PIN: 평문으로 저장하지 않습니다. 교사가 만든 `pinKeys/{방코드}/{PIN해시}`라는 키의 존재 여부로 검증합니다. `pinKeys/{방코드}`는 목록 조회가 막혀 있고 정확한 키만 읽을 수 있습니다. 학생은 해시를 계산해 그 키가 있는지 확인한 뒤, 해시를 담은 `members/{uid}`를 써서 입장합니다. 이 쓰기 자체가 "해당 키가 존재해야만 허용"되도록 규칙이 막고, 이후 방의 모든 읽기는 `members/{uid}`가 있는 사람에게만 열립니다.
- 학번 묶음: `bindings/{학번}`은 최초 한 번만 쓸 수 있고(이미 있으면 거부), 이름이 명단과 같아야 하며, 한 익명 uid는 한 학번에만 묶입니다. 초기화는 교사만 합니다.
- 개별 베팅: `bets/{학번}`은 묶인 본인(과 교사)만 읽을 수 있고, 쓰기는 본인이 베팅 단계(betting)일 때만 가능합니다. 학생에게는 자리별 합계(totals)만 공개됩니다.
- 비공개 데이터: `constraints`(근접 금지 쌍)와 `audit`(추첨 상세 로그, 무효 베팅)는 교사만 읽고 씁니다.
- 결과: `result`는 단계가 done일 때만 방 참여자가 읽을 수 있습니다.
- 단계 전환(phase)은 교사만 할 수 있습니다.

알아 두어야 할 한계

- 6자리 PIN은 경우의 수가 100만 개입니다. Realtime Database 규칙에는 시도 횟수 제한이 없어서, 누군가 익명 계정으로 반복 조회하는 방식의 대입 공격을 막지 못합니다. 이 방식은 "교실 수준의 출입문"으로 생각하세요. 보호 대상은 이름·학번·토큰 수 정도입니다. 더 강하게 지키려면 App Check를 켜거나 PIN을 늘려야 하는데, 그건 이 앱의 범위를 벗어납니다.
- 이름은 비밀이 아닙니다. 입장한 학생은 같은 방의 명단(이름·학번)을 읽을 수 있습니다(최종 배치표에 이름을 보여 주기 위해 필요합니다). 그래서 PIN을 아는 학생이 다른 학생의 학번과 이름을 먼저 입력해 그 학번을 선점할 수 있습니다. 규칙으로는 막을 수 없고, 교사의 [초기화]로 되돌립니다.
- 규칙은 합계를 계산하지 못합니다. 그래서 "한 학생의 합계가 100 이하"와 "합계(totals)가 실제 베팅과 일치"는 규칙으로 강제되지 않습니다. 규칙은 자리별 값이 1 이상 설정값 이하의 정수인지, 활성 자리인지, 베팅 단계인지, 합계의 1회 증감이 설정값 이내인지까지 막습니다. 나머지는 교사 클라이언트가 보완합니다. 교사 화면이 열려 있으면 베팅 중에도 합계를 원본 베팅으로 바로잡고, 마감 때 원본으로 다시 계산해 덮어쓰며, 추첨은 항상 원본 bets를 검증한 뒤 계산합니다. 따라서 합계를 조작해도 추첨 결과에는 영향이 없고, 베팅 중 학생 화면의 숫자만 잠시 어긋날 수 있습니다.
- 같은 기기 자동 로그인은 "같은 브라우저 프로필"을 뜻합니다. 시크릿 모드, 사이트 데이터 삭제, 다른 브라우저로 접속하면 새 익명 uid가 만들어지므로 교사의 초기화가 필요합니다.
- 교사 로그인과 학생 로그인은 서로 다른 Firebase 앱 인스턴스를 써서, 같은 브라우저에서 교사 화면과 학생 화면을 함께 테스트해도 서로의 세션을 덮어쓰지 않습니다.
- Spark 요금제는 동시 접속이 100개로 제한됩니다([Realtime Database 한도](https://firebase.google.com/docs/database/usage/limits)). 한 학급은 교사·TV까지 약 33개 연결이라 괜찮지만, 여러 학급이 같은 프로젝트를 동시에 쓰거나 테스트 방을 많이 열어 두면 한도에 가까워질 수 있습니다. 저장 용량과 월 다운로드 한도도 같은 문서에 있으니 확인하세요. 무료 한도를 넘으면 앱이 중단됩니다.
- 개인정보: 저장하는 것은 학번, 이름, 베팅, 결과뿐입니다. 사용이 끝나면 데이터 탭의 일괄 삭제를 쓰세요. 데이터가 해외 리전에 저장될 수 있으니 학교의 개인정보 지침을 확인하세요.

## 11. 명세와 다르게 구현한 부분

- 결과 공개 시점: 명세는 "저장 후 phase=done"이었지만, 그러면 TV 연출보다 학생 휴대폰이 먼저 결과를 보게 됩니다. 그래서 추첨 결과를 저장한 뒤 phase는 drawing으로 두고(이 동안 result는 교사만 읽을 수 있음), TV 연출이 끝나면 자동으로 done이 되어 학생에게 공개됩니다. 연출 도중 창을 닫았다면 교사 화면의 [결과 공개] 버튼으로 공개할 수 있습니다. 학생 화면은 연출을 다시 재생하지 않고 done이 되면 최종 배치표와 내 자리를 바로 보여 줍니다.
- 추첨 로그의 공개 범위: 공개되는 result에는 배정표, 순서, 유형(베팅/무작위), 시드, 수동 교환 내역만 있습니다. 누가 몇 개를 걸었는지가 드러나는 단계별 확률과 무효 베팅 목록은 교사 전용 `audit`에 둡니다.
- 베팅 데이터 모양: `bets/{학번}`을 `{seats:{자리ID:토큰수}, confirmed, submittedAt}`로 중첩했습니다. 자리 ID와 고정 필드가 같은 층에 섞이면 규칙 검증이 어려워지기 때문입니다.
- 합계 갱신: 트랜잭션 대신 한 번의 원자적 update로 `bets`와 `totals`(서버 `increment`)를 함께 씁니다. 재시도 루프가 없고 중간에 어긋나지 않습니다.
- 추가한 경로: 규칙이 필요로 하는 `members/{uid}`(PIN 검증 통과 표식), `uids/{uid}`(uid에서 학번으로의 역방향 인덱스), `roomIndex/{방코드}`(방 목록용, 교사 전용)가 있습니다. `bindings/{학번}`은 uid 문자열이 아니라 `{uid, name}`입니다. 이름을 규칙에서 명단과 대조하기 위해서입니다.
- 자리 ID는 논리 좌표(`r3c5` = 3행 5열)입니다. 창문·복도 반전과 교탁 위치는 화면 변환일 뿐 자리 ID를 바꾸지 않습니다. 자리 구조와 명단은 준비(setup) 단계에서만 바꿀 수 있습니다.
- 열 수가 분단 수로 나누어떨어지지 않으면 앞쪽 분단부터 한 열씩 더 가집니다. 짝꿍/시험대형은 책상 배치 모양만 다르고, 근접 판정 규칙은 같습니다.
- 마감한 베팅은 추첨 전까지 [베팅 다시 열기]로 되돌릴 수 있습니다.

## 12. 테스트

```
npm install            # 개발용 도구(firebase-tools 등) 설치. 앱 실행에는 필요 없음
npm run test:core      # 추첨 알고리즘 자체 검증 1,000회 (Node, 약 0.3초)
npm run test:rules     # 보안 규칙 82개 시나리오 (Firebase 에뮬레이터 실행, Java 필요)
```

- test:core는 index.html의 순수 함수 영역(`<draw-core>` 표식 사이)만 꺼내 실행합니다. 데모 화면의 자체 검증과 같은 코드입니다. 근접 금지가 만족 불가능한 경우의 대체 배치와 인접 정의도 함께 확인합니다.
- test:rules는 정상 입장·잘못된 PIN·학번 선점·남의 베팅 읽기·음수/초과/비활성 자리 베팅·합계 증감 한도·단계별 잠금·결과 공개 시점·교사 권한을 실제 규칙으로 실행합니다.

실제 Firebase SDK로 앱 전체를 에뮬레이터에 붙여 보려면 에뮬레이터를 켜고(`npm run emulators`) firebaseConfig에 임의의 값을 넣은 뒤 주소에 `?emulator=1`을 붙입니다(Auth 9099, Database 9000에 연결). 이 옵션은 개발용이며 운영 데이터에는 영향이 없습니다.

## 13. 문제 해결

- 로그인 화면에 "Firebase 설정이 비어 있어요"가 보입니다: 4단계의 firebaseConfig를 채우세요.
- "권한이 없어요"가 계속 나옵니다: 6단계의 규칙을 게시했는지, 방 PIN이 맞는지 확인하세요. 교사 계정은 5단계의 /admins 등록이 필요합니다.
- 교사 로그인은 되는데 데이터가 비어 있습니다: databaseURL이 올바른지 확인하세요(리전에 따라 주소 형식이 다릅니다).
- 학생이 "다른 기기에 이미 묶여 있어요"라고 나옵니다: 교사 화면의 제출 현황에서 해당 학생의 [초기화]를 누르세요.
- 연출 소리가 나지 않습니다: 화면을 한 번 클릭하고, 음소거 버튼이 꺼져 있는지 확인하세요.
- 한글 이름이 깨져 보입니다: 가능성은 낮지만 인코딩 자동 감지가 실패한 경우입니다. CSV를 UTF-8로 다시 저장하거나 이름 칸에 직접 붙여넣으세요.
